## Scope

Make the deck physical. Today [`CardStack`](../../app/src/engine-ui/CardStack.tsx) renders the
*front* of the next card at 60% opacity — a spoiler on every card in the deck — and
`GameCard`'s `flipped` prop, specified in 00.3, has no consumer outside `KitchenSink`. This
spec gives the card back a job: the deck is face-down, and a card is revealed by a flip the
participant causes.

**Provisional.** This spec is on trial. If the interaction doesn't hold up in review, the
rollback is the branch — 01.3's behavior is unchanged on `v2`.

### The interaction

1. A round's sort phase opens with the top card **face-down** and the deck beneath it
   face-down. Drag, tap-commit, and the ←/→ keys are inert while the top card is face-down —
   you cannot judge a card you cannot read. This is the one deliberate gate in the loop.
2. A **start affordance** flips the top card face-up. Pointer: click/tap the card. Keyboard:
   `Enter` or `Space` on the focused card. The first flip's direction is fixed (`right`).
3. Committing a card (swipe, ✗/✓ tap, or ←/→) fires the outgoing card's exit **and** the
   next card's flip **concurrently**. The next card is already mounted beneath, so its flip
   plays inside the exit's duration rather than queueing behind it.
4. The flip's direction **follows the commit**: keep (right) flips the next card from the
   right, discard (left) from the left. Derived, never random — the same sequence of
   decisions always produces the same sequence of flips, so the motion survives a refresh
   and reads as the deck responding to the participant.

### `GameCard` — true two-face flip (`app/src/components/GameCard.tsx`)

- Replace the current single-face swap (documented at `GameCard.tsx` as a known shortcut:
  the face swaps at flip *start*, not at the 90° midpoint) with two stacked absolutely
  positioned faces under `transform-style: preserve-3d`, each `backface-visibility: hidden`,
  the back pre-rotated 180°. The rotating element gets `perspective` from a new
  `--card-perspective` token in `app/src/theme/tokens.css`. Required now that the back is a
  distinct face: with a flat accent back the shortcut is invisible; with real art it shows
  value text on a card that is still turned away.
- New prop `flipFrom?: 'left' | 'right'` (default `'right'`) sets the sign of the back
  face's rotation, so the same `flipped` transition can turn either way.
- New prop `initialFace?: 'front' | 'back'` (defaults to `flipped`) names the face the card
  **mounts** on, separately from the face it is animating **toward**. Load-bearing, not
  ornamental: the deck card is remounted at commit time with `flipped` already `false`, so
  deriving the start face from `flipped` resolves start and target both to the front and the
  card animates front-to-front — a face swap with `transform: none` and no rotation at all.
  Every "ends face-up" assertion still passes, which is why the rotation is sampled mid-commit
  in `e2e/sort-flip.spec.ts`.
- New prop `flipDelay?: number` (seconds, ignored under reduced motion) holds the flip back so
  something else can clear the stage first.
- The back face stays the pack-supplied accent fill. Facilitator-uploaded `cardBackArt` is
  **03.3**'s; this spec is the consumer that makes it visible, and must leave the back face
  as a single element that 03.3 can paint.
- Timing reuses the existing `FLIP_SPRING` mirroring `--spring-stiffness` / `--spring-damping`.
  No new timing token: the flip is a doorway in a 40-card loop, not a destination, so it
  stays fast.
- Reduced motion is unchanged in mechanism — `fadeOnlyVariants` strips `rotateY`, so the
  reveal degrades to the shared ≤150 ms crossfade and `flipFrom` has no effect. Nothing in
  the interaction may depend on the flip's duration or direction.

### `CardStack` — face-down deck + overlapping flip (`app/src/engine-ui/CardStack.tsx`)

- The peeking next card renders face-down and **static** — no flip on arrival, no opacity
  spoiler. Remove the `opacity-60` front render.
- Two pieces of local state, and no more: `revealed` (has the top card been turned up) and
  `pendingFlip` (`null` or the direction of an in-flight commit).
- New `SwipeCard` callback `onCommitStart(direction)` fires when the commit animation
  *begins*, not when it resolves. `CardStack` sets `pendingFlip` from it, which flips the
  peeking card face-up while the outgoing card is still exiting.
- The flip is held back by `FLIP_LEAD_SECONDS` (0.12s). **Total overlap is wrong**: the
  committed card sits directly on top of the deck card and takes ~120ms to slide clear, so
  starting both at the same instant hides the entire turn behind the departing card — the
  reveal reads as the next card simply appearing face-up. The turn has to begin *as* the
  stage clears. This is still overlap, nowhere near the ~600ms serial cost of flipping only
  after the store advances.
- When the `card` prop changes (the store advanced), reset `pendingFlip` to `null`. The
  incoming active card mounts **already face-up** with no transition — it is the same card
  the participant just watched flip, at the same rotation, so the swap is invisible.
- `revealed` starts `true` on a **resumed** round and `false` on a fresh one. Signal:
  `kept.length + discarded.length === 0` for the current round means nothing has been sorted
  yet. A mid-round refresh must never put a face-down card in front of someone 22 cards deep
  (tenet 6, invariant 4); someone who has sorted nothing has not begun, so a face-down deck
  is correct for them. `SortRound` passes this down; `CardStack` does not read the store.
- Because `SortRound` renders for every `phase === 'sort'`, the face-down start happens at
  the top of **each** round, not once per session. That is intended: it is participant-
  initiated, so it reads as "begin this round" rather than a replayed cutscene.
- **The deck has thickness**: `DECK_DEPTH` (2) static, inert, `aria-hidden` face-down cards
  are drawn behind the turning card at `DECK_STEP_PX` increments. A one-card-deep deck has no
  stack — the single card behind the active one *is* the card that flips, so the instant it
  turns the slot is empty and a replacement pops in after the store advances. The backs also
  give the turn's edge-on frames something to land against: at exactly 90° both faces are
  `backface-visibility: hidden`, so a zero-thickness card is briefly invisible. Count thins
  honestly near the bottom of the deck (`remaining - 2`).
- `DECK_STEP_PX` (4) is bounded by the control row, not by taste: the stack hangs
  `DECK_STEP_PX * (DECK_DEPTH + 1)` below the active card and `SwipeCard` puts the commit
  controls 16px beneath it, so the product must stay under 16 — at a step of 8 the deck
  overhung the buttons by 8px. Raising either constant requires lowering the other or making
  room below the card. Held by geometry in `e2e/sort-flip.spec.ts`, not by the constant.
- Last card: `nextCard` is already optional. With an empty deck there is nothing to flip and
  the commit animates alone.

### Interruptibility (`app/src/engine-ui/SwipeCard.tsx`)

- The flip is never a gate on input once the card is face-up: drag and ←/→ stay live while a
  flip is still settling, and a commit is accepted immediately rather than queued.
- **Decision:** a commit mid-flip lets the card exit while still rotating; it does not snap
  the rotation to 0 first. The window only exists for the first card of a round (later cards
  flip on the *peeking* card behind the re-entry guard, so there is no window at all), and a
  snap costs a special case in the one place the motion is already correct. Revisit only if
  review finds the mid-rotation exit reads as broken.
- Guard commit re-entry: a second commit while one is already animating is a no-op. Today
  `commit()` is `void`-called from both the keydown handler and `handleDragEnd` with no
  re-entry guard, so holding `→` can call `onKeep` more than once for the same card.

## Out of scope

- **Wall reveal flip** — deferred by decision. A face-down tile for joined-but-unrevealed
  participants and a flip on reveal would retrofit `Wall.tsx`'s `buildTiles`; not this spec,
  and not currently owned by any spec.
- **Facilitator card-back art** (`cardBackArt` upload, extraction, palette validation) →
  **03.3**. This spec only guarantees the back face exists and is visible.
- **Deal-in / shuffle ceremony** — considered and rejected: a per-round ceremony that covers
  no real latency, in exchange for the one moment the start affordance already provides.
- Trim, rank, and round-transition surfaces → **01.4** (unchanged; `TrimGrid` stays a
  face-up comparison grid, where face-down would defeat the task).
- Pack-swappable back treatment → **00.6**.

## Acceptance criteria

- [x] `GameCard` stacks two faces with `backface-visibility: hidden` and the back
      pre-rotated, inside a `preserve-3d` element under a `--card-perspective` wrapper
      (`app/src/components/GameCard.test.tsx`; computed styles asserted in
      `e2e/sort-flip.spec.ts`).
- [x] `flipFrom` inverts the rotation sign — asserted on the exported pure `flipTarget()`,
      the same pattern 01.3 used for `swipeExitTarget`, so the rule is testable without
      animation frames (`GameCard.test.tsx`).
- [x] No front-face content of the next card is present in the DOM while it is face-down —
      the front face is only mounted face-up, so this is asserted as *absence*, not opacity
      (`card-stack.test.tsx`, plus `e2e/sort-flip.spec.ts` asserting exactly one
      `card-front` on screen).
- [x] A fresh round renders the top card face-down with drag and ←/→ inert; the turn-over
      control flips it face-up and arms them (`card-stack.test.tsx`,
      `swipe-card.test.tsx`, `e2e/sort-flip.spec.ts`).
- [x] Keyboard equivalence: `Enter` and `Space` both turn the card over from a focused card,
      and a full round completes with keys only (`swipe-card.test.tsx`,
      `e2e/sort-flip.spec.ts`, `e2e/sort-keyboard.spec.ts`, and the keyboard-only
      `e2e/solo-journey.spec.ts` across all three rounds).
- [x] The card's accessible name is its value from the moment it is the active card,
      regardless of flip state — the flip never hides the card from assistive tech
      (`swipe-card.test.tsx`).
- [x] `onCommitStart` fires before the commit resolves — ordering asserted explicitly
      (`swipe-card.test.tsx`), and `e2e/sort-flip.spec.ts` asserts the next card arrives
      face-up with no second turn-over.
- [x] The deck card's rotation is **sampled mid-commit** and passes through intermediate
      angles — `transform: none` or a hard 180°→0° jump both fail. Verified falsifiable:
      removing `initialFace="back"` takes the mid-turn sample count from >2 to 0 while every
      other assertion in the suite still passes (`e2e/sort-flip.spec.ts`).
- [x] `initialFace` decouples mount face from target face (`GameCard.test.tsx`).
- [x] The deck is drawn with thickness: `nextCard` plus 2 static face-down backs, all
      `aria-hidden`, thinning honestly at the bottom of the deck (`card-stack.test.tsx`,
      `e2e/sort-flip.spec.ts`). Per-frame instrumentation confirmed the pre-fix behaviour:
      exactly 2 cards on stage, so the deck slot emptied for the whole turn.
- [x] The deck clears the commit controls **at rest** at 390px and 1280px, in both the
      face-down and face-up states — asserted on measured geometry so raising `DECK_DEPTH` or
      `DECK_STEP_PX` fails here rather than in review. Verified falsifiable: restoring an 8px
      step fails it. Mid-rotation the card projects a taller box under perspective, which is
      the turn and not a layout fault, so the assertion polls for the settled layout.
- [x] Effective opacity (multiplied through every ancestor) is constant at 1.00 for every
      card on stage across the whole commit — the apparent dimming of the deck is *occlusion*
      by the active card's translucent panel, not a fade, so it is not fixable by changing
      opacity values. Measured, not assumed.
- [x] Flip direction follows the commit: keep → `'right'`, discard → `'left'`
      (`flipFromCommit` unit test). No randomness in the flip path.
- [x] Re-entrant commits are no-ops: three rapid `→` presses commit once
      (`swipe-card.test.tsx`). This was a latent 01.3 double-count, not just a 01.5 concern.
- [x] **Invariant 4 (PRD §6.4):** `e2e/sort-flip.spec.ts` sorts 3 cards, reloads, and
      asserts the restored active card is **face-up** with no turn-over control;
      `e2e/sort-refresh.spec.ts` still proves progress itself survives.
- [x] With reduced motion emulated, the reveal renders as a fade — the resting transform has
      no rotation component (`e2e/sort-flip.spec.ts`, `e2e/reduced-motion.spec.ts`).
- [x] The face-down state is asserted **in a real browser**, not only in jsdom. Non-optional:
      the first implementation guarded the reveal with a has-mounted ref, which survives
      `StrictMode`'s effect/cleanup/effect cycle — every jsdom test passed while the deck
      revealed itself on mount in the browser (`e2e/sort-flip.spec.ts`).
- [x] **iOS/WebKit compositing verified.** `.card-face` puts `backdrop-filter` (via
      `.glass-panel`) inside a `preserve-3d` context alongside `backface-visibility: hidden` —
      a combination WebKit has historically flattened, which would blank a face or kill the
      turn. Checked against real WebKit 26.5 (desktop Safari + iPhone 14) via
      `pnpm check:webkit`: `preserve-3d` survives, `backface-visibility` is honored,
      `backdrop-filter` still applies, both faces paint, and the deck card rotates through
      intermediate angles. 14/14 assertions pass, so **no fallback is needed** and
      `.card-face` keeps the panel blur.
- [x] The WebKit check is repeatable, not a one-off: `scripts/webkit-flip-check.mjs`, run with
      `pnpm check:webkit`. Deliberately a script rather than an `e2e/*.spec.ts` — discovery is
      include-by-default, so a spec would join every gate run, and `playwright.config.ts` has
      no WebKit project to run it under. Continuous WebKit coverage is **04.2**'s call.
- [x] `pnpm gate` green — typecheck, lint, token lint (`--card-perspective` declared in
      `app/src/theme/tokens.css`; `app/src` clean), 314 unit tests, 100 E2E.
