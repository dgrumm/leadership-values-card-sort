## Scope

`RevealSnapshotSchema.cards` becomes `number[]` — indices into `config.deck.cards` — instead
of a copy of the `Card` objects. Purely a storage-shape change: nothing about what gets
revealed, when, or to whom changes.

### Why

A session's entire `SessionState` is one Durable Object storage value, capped at 128KB
(architecture §12), and reveal snapshots copy full `Card` objects **per participant, per
round**. That term dominates the total, so 00.2's card-text bounds (added by 03.2) are
necessary but not sufficient. Measured serialized `SessionState`, 100-card deck at the
00.2 text ceilings:

| `reveals` stores | 12 participants, keeps 8/3 | 40 participants, keeps 50/25 |
| --- | --- | --- |
| full `Card` objects (today) | 92.2KB | 1192.9KB ❌ |
| card values only | 50.1KB | 234.9KB ❌ |
| **deck indices** | **42.2KB** | **58.4KB** |

Today's real sessions (bundled decks, ~6 people) sit at 14–24KB, which is why this has
never bitten — but a 100-card custom deck at 12 participants is already at 72% of the
limit, and `storage.put` throws past it.

### Changes
- `shared/src/schemas/session.ts` — `RevealSnapshotSchema.cards: z.array(z.number().int().nonnegative())`.
- `shared/src/engine/apply-intent.ts` — the `reveal` keep-count check counts indices;
  add validation that every index is in range for the session's deck, and that indices
  within one snapshot are unique. An out-of-range or duplicate index is a rejection,
  not a clamp.
- `app/src/routes/wall/` (02.3) and any reveal rendering — resolve `config.deck.cards[i]`.
  Ranked order is still the array order, so ranking is unaffected.
- Reveal payload construction on the client — send indices, which also shrinks the intent.

### The load-bearing assumption
Indices are only meaningful against a frozen deck. This already holds: `updateConfig` is
rejected once `phase !== 'lobby'`, and reveals only exist while `active`. That was
incidental before and is now load-bearing, so it needs its own explicit test rather than
relying on the existing lobby-only test.

## Out of scope
- Any change to what a reveal contains semantically, or to reveal/un-reveal behavior → 02.2.
- Card-text bounds → done in the 00.2 amendment under 03.2.
- A participant cap → 04.2 (see note below).

## Acceptance criteria
- [ ] `RevealSnapshotSchema` accepts an index array and rejects `Card` objects, negative
      indices, non-integers, and duplicate indices within a snapshot (`session.test.ts` in `shared/`).
- [ ] A reveal whose index is out of range for the session's deck is rejected server-side
      (party test), not clamped or silently dropped.
- [ ] Keep-count enforcement (PRD §6 invariant 3) still holds on index payloads — the
      existing invariant test passes against the new shape.
- [ ] Write-once semantics (invariant 2) unchanged: un-reveal deletes, never edits.
- [ ] `updateConfig` cannot change the deck once any reveal exists — explicit test, since
      index validity now depends on it.
- [ ] Results wall renders revealed cards resolved through `config.deck.cards`, including
      ranked order, with no visual change (existing wall E2E passes unmodified).
- [ ] Budget test: `SessionState` with a 100-card deck at the 00.2 text ceilings,
      40 participants, and keeps 50/25 serializes under 128KB (unit test).
- [ ] `pnpm gate` green.

## Note for 04.2 Hardening
There is no participant cap anywhere in the code. The PRD targets 6 and load-tests 12,
but nothing enforces a ceiling, and participant count is a linear multiplier on the
reveals term above. Worth an explicit cap in 04.2 rather than leaving it implicit.

Also observed while measuring this: `party/src/session.test.ts`'s "two participants named
Dave Smith … distinct avatarHues" test asserts a distinctness the code doesn't guarantee —
`avatarHue` is `hash(uuid) % 360`, so two participants can legitimately collide in one of
360 buckets. It flakes. Fixing that assertion belongs in 04.2.
